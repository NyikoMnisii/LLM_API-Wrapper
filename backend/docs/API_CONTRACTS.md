# API Contracts — Agrilite AI Agronomist API

> Hand-written companion to the live OpenAPI spec (`/openapi.json`, browsable at
> `/docs`) generated by FastAPI. The live spec is the executable source of truth for
> exact JSON Schema; this file exists so contracts can be reviewed/diffed in a PR
> before an endpoint is built or changed, per the PRD's change process.
> Last updated: 2026-08-06. Base path: `/api/v1` (configurable via `API_PREFIX`).

## Authentication

`POST /chat` and `GET /weather/forecast` require `Authorization: Bearer <token>`,
where `<token>` is a Supabase access token (from `supabase.auth.getSession()` on the
client — the frontend attaches this automatically, see `frontend/src/api/client.ts`).
The token is verified against the Supabase project's JWKS (`app/core/auth.py`); a
missing, malformed, or invalid/expired token gets a `401` in the standard error
shape (see Error Contract). `GET /health`, `/health/ready` are unauthenticated.
There is no authorization beyond "is this a valid Supabase user" — no per-user data
access is currently gated by identity.

## POST /chat

Structured, weather-grounded agronomy advice from a single conversational turn.

**Request** (`ChatPayload`, `app/models/chat.py`)
```json
{
  "message": "Should I water my maize today?",
  "history": [
    { "role": "user", "content": "previous turn text" },
    { "role": "model", "content": "previous model reply text" }
  ],
  "latitude": -33.9346,
  "longitude": 18.8668
}
```
- `message` (string, required)
- `history` (array, optional, default `[]`) — the client is responsible for
  resending prior turns; the server holds no session state (see PRD §6).
- `latitude` / `longitude` (float, optional) — the client's device-resolved
  location. When present, weather-related questions that don't name a specific
  place ("is there frost risk today?") are automatically grounded in this
  location — the model is instructed not to ask the user to type it. Omit either
  field to fall back to free-text location search only (the model will ask the
  user to name a place if needed).

**Response 200** (`AgronomistResponse`, `app/models/agronomist.py`)
```json
{
  "analysis": "There is no frost risk in Stellenbosch over the next 3 days...",
  "recommendations": ["Monitor crops for fungal disease...", "..."],
  "sustainability_note": "Avoid applying contact fungicides immediately before rain...",
  "is_farming_related": true
}
```
- `is_farming_related: false` indicates the query was off-topic; `analysis` will
  contain a polite redirect rather than farming advice.
- When the underlying weather tool can't resolve a location, `analysis` carries the
  clarification prompt verbatim and `recommendations` is empty — the model is
  instructed not to fabricate advice for an unresolved location.

## GET /weather/forecast

Direct access to the same weather-risk logic the chat tool uses, bypassing Gemini
entirely. This is what a home-screen "current weather" view calls directly, as well
as anything that wants the raw forecast without a chat turn. Same response shape
either way — see PRD's Location Resolution Strategy decision for why there's no
separate lightweight "current conditions" endpoint.

**Query parameters** — provide *either* `location` *or* both `latitude`+
`longitude`. If both are given, coordinates win (they're unambiguous; free text
isn't). Providing neither is a `422 InvalidRequestError`.

| Param | Type | Required | Notes |
|---|---|---|---|
| `location` | string | one-of | Free-text place name; may return `REQUIRES_CLARIFICATION` |
| `latitude` | float | one-of (with `longitude`) | Device-resolved latitude; skips geocoding, never ambiguous |
| `longitude` | float | one-of (with `latitude`) | Device-resolved longitude |
| `location_label` | string | no | Only used with `latitude`/`longitude`; echoed back as `resolved_location` for display. The backend does not reverse-geocode. |
| `days` | integer | no (default 3) | Clamped server-side to 1–7 |

**Response 200** (`WeatherForecast`, `app/models/weather.py`) — example via
free-text `location`:
```json
{
  "status": "SUCCESS",
  "reason": null,
  "resolved_location": "Stellenbosch, Western Cape (South Africa)",
  "dates": ["2026-08-04", "2026-08-05", "2026-08-06"],
  "min_temperatures_celsius": [12.4, 9.4, 9.3],
  "max_temperatures_celsius": [23.8, 17.1, 13.2],
  "total_precipitation_mm": [0.0, 0.2, 25.1],
  "frost_warning": false,
  "high_humidity_fungal_risk": true
}
```
Example via `latitude`/`longitude` (home screen) — identical shape, only
`resolved_location` behaves differently:
```json
{
  "status": "SUCCESS",
  "reason": null,
  "resolved_location": null,
  "dates": ["2026-08-06", "2026-08-07", "2026-08-08"],
  "min_temperatures_celsius": [9.1, 8.7, 10.2],
  "max_temperatures_celsius": [21.4, 19.8, 22.0],
  "total_precipitation_mm": [0.0, 4.2, 0.0],
  "frost_warning": false,
  "high_humidity_fungal_risk": false
}
```

`status` is one of:
- `SUCCESS` — forecast fields populated. `resolved_location` is a geocoded display
  name on the free-text path, the client-supplied `location_label` (or `null`) on
  the coordinate path.
- `REQUIRES_CLARIFICATION` — free-text location not found, or genuinely ambiguous
  between distinct populated places (see `ARCHITECTURE.md` §5). **Cannot happen on
  the coordinate path** — coordinates are unambiguous by construction. `reason`
  holds a human-readable prompt; forecast arrays are empty.
- `ERROR` — Open-Meteo returned no usable forecast data for a resolved location.

This endpoint never raises 4xx/5xx for a bad *location name* — that's a `200` with
`status != SUCCESS`, by design, so a client can render it without special-casing
HTTP errors for what is really a "need more input" conversational state. Missing
*both* `location` and coordinates is a genuine client bug, not a "need more input"
state, so that alone gets a real 422 (see Error Contract).

```json
{ "status": "ok" }
{ "status": "ready" }
```

probe.

## Error Contract

Raised application errors (`app/core/exceptions.py`) are returned as:
```json
{ "error": "<human-readable detail>" }
```
| Exception | HTTP status | Raised from |
|---|---|---|
| `ExternalAPIError` | 502 | `OpenMeteoClient` on a failed geocode/forecast HTTP call |
| `ToolExecutionError` | 500 | `ToolExecutor` when Gemini requests an unregistered tool name |
| `LLMGenerationError` | 502 | `GeminiService` on a malformed/empty/unparsable model response |
| `AuthenticationError` | 401 | Missing/malformed `Authorization` header, or an invalid/expired Supabase access token |
| `InvalidRequestError` | 422 | `GET /weather/forecast` when neither `location` nor `latitude`+`longitude` is provided |
| any other unhandled `Exception` | 500 | generic fallback, logged server-side with full traceback |
| `RateLimitExceeded` (slowapi) | 429 | per-IP rate limit exceeded |

Note: `LocationNotFoundError` and `AmbiguousLocationError` are defined in
`app/core/exceptions.py` but currently unused — location resolution failures are
communicated via `WeatherForecast.status`, not exceptions (see above). Listed here
so this doc doesn't silently imply they're live; remove or wire them up
intentionally rather than leaving them as ambiguous dead code.

Every response carries an `X-Request-ID` header (echoed from the request if
provided, otherwise generated) for log correlation.
